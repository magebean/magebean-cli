# Current-state mission QA — part 1

## Assigned scope and method

Read-only review of the first **38 of 110 active Magebean catalog entries**, in current catalog order, from MB-0001 through MB-0067. These are not the first 38 numerical IDs: reserved/retired gaps remain absent. No production source, rules, profiles or retirement classifications were changed by this review.

Mission used for this review: describe the assessed project's **current observed state, risks and unresolved evidence**, with enough context to decide scope. A coding preference, architecture choice, arbitrary threshold or upstream activity signal must not silently become a confirmed vulnerability. Observing a configuration value can be highly certain while the resulting business/security impact remains uncertain.

Every row was checked against its actual catalog arguments, handler implementation and built-in profile memberships. A supplemental fixture runner is provided at `tools/current-state-part1-probes.php`. It uses temporary files, SQLite snapshots and a loopback advisory feed; it does not query customer services or remote feeds. Actual execution results are recorded separately below when available. Missing-input tests alone are not used to infer impossibility of automation.

Implementation paths below are relative to `src/Engine/Checks/`. Handler references point to reviewed workspace lines. The nominal severity/lane labels are catalog values, not a claim that all rendered detector observations necessarily use that severity.

## Main findings

1. **Policy observations are mixed into security risk reporting.** MB-0006 (uncommon Admin route), MB-0014 (any direct superglobal), MB-0040 (Redis session architecture/password declaration), MB-0065/0066 (Composer constraint styles) and MB-0067 (explicit prefer-stable flag) are currently high-severity security-lane rules. Their facts may be correct, but those facts alone do not establish an exploitable current-state weakness. Keep the observations and give them an explicit policy/maintenance context.
2. **Advisory findings can be counted repeatedly.** MB-0049 audits the complete lock inventory; MB-0055 passes its transitive subset back to the same `auditApi`; MB-0056 and MB-0059 derive upgrade-constraint/publication-age information from the same advisory audit. Prefer one package/version/advisory finding with dependency-path, remediation and age metadata. Different scopes remain useful evidence; they are not four separate vulnerabilities.
3. **Lock inventory is not installed production inventory.** MB-0049/0055 read lock `packages-dev` as well as `packages`. This is correct for their literal lock-scope criteria, but a production `--no-dev` installation can therefore receive findings for components absent from installed metadata. Label build/development versus deployed scope or support an explicit installed-production inventory. Do not silently drop development risk when auditing a development checkout.
4. **Maintenance age and repository activity are context, not vulnerability proof.** MB-0062 reports age of the latest package release, not support/EOL; MB-0063 reports archive/missing status, not exploitability. MB-0061 reports abandoned status, not actual usage reachability or downstream support. Keep these factual signals, with source timestamp and explicit maintenance policy.
5. **Cron/indexer snapshots need interpretation.** A working indexer can be healthy current activity. A recent cron execution may be an error. A low pending count does not establish successful dispatch. The predicates are separate facts and should remain complementary evidence, rather than conflicting global “healthy/unhealthy” labels.

## Cross-profile implications

- `basic` contains route-name/MFA/configuration/transport/advisory observations, so policy and runtime facts already mix in a common user workflow.
- `development` among these 38 includes MB-0029 only; absence of runtime rules here is appropriate. Other development-specific rules are reviewed in the other QA parts.
- `prelaunch` among these 38 includes local declarations/artifact presence and HTTP observations. These are complementary evidence scopes; they do not by themselves correlate the current source tree with the tested deployed build.
- `takeover` intentionally includes maintenance and architecture policies (MB-0038/0040/0062/0065–0067). Keep that information for scoping, but separate confirmed technical risk, configurable policy deviation, maintenance context and missing access.
- `hardening`/`owasp-top-10-2025` include repeated advisory-derived rules; preserve coverage while grouping one underlying advisory issue. A policy check's presence in a security-themed profile does not strengthen its evidence.

## Confidence and remediation conclusions

- Preserve confidence in the exact observed fact: a date field, declaration, permission bit or returned header may be confirmed. Do not transfer that certainty automatically to exploitation, ineffective authentication, unsupported software or a production incident.
- For policy-only recommendations, remediation should begin with the approved architecture/build policy and component purpose, then propose a concrete change if that policy actually applies. Avoid mandatory Redis migration, cosmetic Admin-route changes or mass Composer constraint edits as universal “security fixes”.
- Advisory matching should retain source/feed revision, package inventory scope, affected version, missing severity and verified local patch evidence. Merge duplicate risk presentation; keep distinct evidence obligations and collection gaps.
- No rule retirement, catalog reclassification or production fix was performed in this read-only review. The findings support explicit context and evidence improvements rather than another blanket removal of automation.
