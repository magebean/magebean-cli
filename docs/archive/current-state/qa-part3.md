## Material findings and prioritization

1. **P1/P2 correctness: inherited private constructor can be certified as instantiable.** `MagentoDiCheck::concrete()` inspects the target class’s own constructor only. A child implementing the desired contract but inheriting a private constructor is accepted by preference inspection; actual synthetic PHP instantiation throws an Error. The shared helper affects MB-0815, MB-0816 and plugin class checks in MB-0818. Resolve inherited construction or report incomplete coverage.
2. **P2 input validation: MB-0805 accepts an empty package version with a matching approved source declaration.** The direct probe produces PASS for both `1.0.0` and `""`. This is incomplete lock-input validation, not evidence that the approved source URL/reference is wrong. Validate canonical package names/nonempty versions and list scope before claiming complete collected package inventory.
3. **Coverage limitation: callable arrays in MB-0817.** The helper returns ok for type=array against a callable constructor parameter without examining callable shape or target. Either explicitly narrow this to potential type compatibility or return UNKNOWN unless the callable construction is supported.
4. **Potential duplicate findings:** MB-0795/MB-0814 on app/code logger arguments; MB-0780/MB-0800 on upload filenames; MB-0790/MB-0822 on request command calls; MB-0786/MB-0822 on query syntax/flows. Keep distinct evidence scopes but group shared locations/root causes so totals are not mistaken for independent vulnerabilities.
5. **Policy and advisory findings need labels.** Strict native API/literal HTTPS bans, approval/source/mitigation-record policies, empty catches and loop query observations have legitimate uses. They should not be presented as confirmed exploitable security vulnerabilities. Current precise criteria and optional capability gates help; the default UI hides confidence/category by user choice, making accurate titles/messages particularly important.

## Profile/scope implications

- Development: source/declaration/compatibility/reliability checks fit ordinary checkouts when installed dependency context is available. DB/worker/runtime response predicates belong to explicit installed-target scopes and capability contexts, not automatic source-only prerequisites.
- Prelaunch: configured target URL and local release path are evidence scopes, not proof they are the same deployed build. Source defects and runtime policy findings should retain that distinction.
- Takeover/hardening: policy records and strict architectural bans can help discovery when the agency supplies the policy. Absence of policy context must remain an omission/gap rather than inventing a universal requirement.
- A successful bounded snapshot can support an exact local predicate. It cannot establish end-to-end checkout correctness, every API authorization path, full deployment safety, all worker processes, all dependency provenance truth, comprehensive vulnerability absence or appropriate business privilege.
