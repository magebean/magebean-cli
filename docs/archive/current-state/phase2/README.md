# Phase 2 — dependency and observation provenance

Phase 2 separates installed metadata, locked build intent, development dependencies and declared module state. It does not deploy to a customer store or establish runtime reachability. Profile memberships and the planned Phase 5 rollout remain unchanged.

## Implemented behavior

- One `DependencyInventory` reads Composer lock/root metadata and installed JSON as data, preserving input paths, content hashes and an observation time. Configured relative vendor directories are supported; installed.php is not executed. Ambiguous duplicate identities cannot be selected arbitrarily. Package-supplied fields cannot override collector provenance.
- General package advisory and online maintenance/repository checks prioritize recorded installed versions when installed metadata exists. A production no-dev install excludes packages present only in packages-dev. A dev dependency actually recorded as installed is still assessed. Installed version drift from the lock remains visible instead of querying the wrong locked version.
- Without installed metadata, source-checkout results explicitly use locked_dependency scope and leave installation unverified. Existing invalid installed metadata cannot silently turn into a clean lock-based runtime conclusion. Supported findings from valid records survive incomplete peers; incomplete inventory cannot establish a clean result.
- Existing explicitly locked-build predicates (Magento locked-release patch checks, yanked versions and direct/Marketplace latest-version policies) retain their declared basis and now expose locked_dependency provenance. They do not silently become installed-runtime predicates; their scope wording makes the build observation explicit.
- Evidence adds dependency_inventory, package_observations and per-advisory dependency_observation fields. These distinguish source path, version, installed state, development provenance, exact lock-version agreement and unverified reachability. Module enablement is a separate source declaration, not proof that a package is used in a request. The module collector shares installed metadata and flags observed declaration drift.
- Related advisory views (MB-0049/0055/0056/0059, plus compatible selectors) share successful validated API replies within one bounded collection session. Cache keys retain endpoint, request, timeout and authentication separation. Invalid transport/schema replies are not retained as successful observations. New scans start fresh; store HTTP/process probes remain fresh. Existing service endpoints and upstream managed cache behavior are retained.
- Failed advisory/status batches preserve findings established by other batches. Missing batches cannot yield clean coverage. Publication-age and dependency-constraint views retain the selected inventory scope; constraint checks remain declaration/build feasibility observations, not runtime proof.
- The opt-in MB-0828 supplied snapshot uses the same dependency selection and common advisory evaluator, with explicit supplied-record coverage. It does not reuse an unrelated online feed or claim snapshot completeness/freshness. Development source checks remain usable offline; no new .magebean/osv-db.json file or directory is fabricated or made mandatory.
- Literal PHP config arrays share a passive observation within a scan. Unsupported executable/dynamic legacy config retains its existing evaluation frequency; strict restored static predicates remain passive and bounded. Project ini reads use the shared file collector. Source declarations, resolved configuration, process and HTTP observations retain separate meanings.
- MB-0039 treats invalid database rows as readiness issues. Working rows alone yield UNKNOWN and include update age where available; age alone is not a stuck-process diagnosis. Cron execution freshness includes recent error/running activity and explicitly does not establish successful completion. Pending backlog remains a separate fact from success and heartbeat.

## Qualification

- All 139 CLI test files passed after the final code changes. The module/profile tests also cover the declaration-drift guard.
- `CurrentStatePhase2ProvenanceTest.php`: 42 assertions, using synthetic metadata, a loopback API and in-memory SQLite. It covers no-dev, installed dev packages, version drift, invalid and duplicate metadata, custom vendor-dir, forged provenance fields, partial feeds/statuses, session cache isolation, literal/dynamic config and operational facts.
- All six original Phase 2 QA observations pass their expected scope/outcome. `acceptance-results.json` points to `part1-probes.json`; the latter retains other observations for later phases and is not a claim they are fixed.
- Compatibility snapshot differences were reviewed: only offline advisory scope wording and additive provenance fields changed. Observation timestamps are normalized; unrelated CLI/agent/standard snapshots did not change.
- Both standard and one-time PHARs run the same 42-assertion regression through their own archived autoloader as a publication gate, alongside Phase 1, restored-rule and profile qualification.
- Historical Phase 0 acceptance, protected ASVS/PCI definitions and the retirement archive remain unchanged. Eight Magebean criteria were revised for the new scope: MB-0039/0049/0055/0059/0062/0063/0744/0828. Active counts remain 110 Magebean and 14 built-in profiles.

Validation is synthetic and local; no live-store qualification is implied. Phase 3 follows with category/confidence and policy boundaries; correlation/grouping is Phase 4 and restored-rule profile membership is Phase 5.
